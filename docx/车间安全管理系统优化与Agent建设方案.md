# 车间安全管理系统优化与 Agent 建设方案

> 检查日期：2026-11-09
> 依据：项目源码、Prisma 模型与迁移、现有设计/知识库/部署文档、《车间安全管理系统优化建议》
> 目标：先让确定性安全业务“可信、可追溯、可恢复”，再以只读工具型 Agent 提升检索、统计解释和草稿编写效率。

---

## 一、执行结论

### 1. 当前定位

项目已经具备较完整的业务系统与 AI 辅助能力：

- React 19 + Vite 前端、NestJS + Prisma 后端、PostgreSQL + pgvector。
- 隐患手工录入、PPT/Word/Excel 解析、照片、整改与复查、检查计划、提醒、统计、考核、法规、回收站。
- 本地嵌入模型、语义检索、DeepSeek 问答、AI 预标注、范例学习、文字规范检查。
- 钉钉通报自动导入、每日备份、Windows 看门狗和 Docker 部署骨架。

但当前仍是“固定业务接口 + RAG/单次模型调用”，**尚不是工具型 Agent**：没有工具规划循环、任务级状态机、步骤轨迹、业务验收器、成本控制、暂停恢复和系统评测。

### 2. 核心决策

1. **不在当前状态直接给 Agent 开放业务写工具。** 先修复虚假完成、闭环绕过、权限与审批、导入幂等和 AI 运行控制。
2. **不引入多 Agent，不先引入重型 Agent 框架。** 在现有 NestJS 中实现一个有界、单 Agent、只读工具循环即可，减少新基础设施和排障层级。
3. **Agent 的成功不能由模型自己声明。** 统计数值由 SQL/确定性服务计算，引用由后端校验，任务成功由业务验收器判定。
4. **AI 只生成建议和草稿。** 隐患闭环、正式考核、制度变更继续由确定性命令、人工复核与审批完成。
5. **不对当前项目打主观百分制分数。** 尚无任务成功率、首次通过率、P95、人工修正时间和单成功任务成本实测数据。

### 3. 上线门禁

以下任一项未通过，都不应扩大 AI/Agent 使用范围：

- 虚假完成率为 0。
- 高风险审批绕过率为 0。
- 重复提交/超时重试不产生重复业务记录。
- 未满足整改证据、复查和审批条件的记录不能闭环。
- 提示注入不能触发危险操作或越权读取。
- AI 故障不影响隐患录入、整改、查询等主业务。
- 高风险操作可审计、可停止、可恢复。

## 三、现状问题清单

## 3.1 P0：安全与正确性否决项

### P0-1：前端仍存在“虚假完成”

**证据**

- `app/src/lib/store.tsx` 的 `addIssue/addIssues/updateIssue/...` 类型均返回 `void`，内部 `run()` 不返回 Promise。
- `IssueEntry.tsx` 手动录入调用 `addIssue()` 后立即跳转。
- 批量导入调用 `addIssues(items)`、核销调用 `updateIssue()` 后，没有等待服务端结果，就设置成功、等待 1.4 秒、清空草稿并跳转。

**后果**

后端 400/500、断网或数据库失败时，用户仍可能看到成功并丢失暂存数据；重试又可能重复上传照片或重复入库。

**改造**

所有写操作返回 `Promise<实体/批次结果>`；只有服务端成功并重新查询确认后才清草稿。草稿与照片元数据先持久化到 IndexedDB，失败保留，支持继续、重试和转人工。

---

### P0-2：通用编辑接口可以绕过闭环状态机

**证据**

`issues.service.ts` 的 `WRITABLE` 仍允许直接写：

- `status`
- `closedAt`
- `rechecks`
- `reviewed`

前端问题库通过通用 PATCH 推进 `pending → fixing → review → closed`；通报核销也直接写 `status=closed`。后端没有统一校验“整改证据、规定复查、阶段完成、审批通过”这些闭环前置条件。

`stage/next` 只限制阶段顺序，与 `status=closed` 没有形成统一不变量，因此可出现“阶段未完成但状态已闭环”。

**改造**

- 通用 PATCH 移除上述高风险字段。
- 建立后端唯一业务命令层：提交整改、验收整改、登记复查、申请闭环、审批闭环、撤销闭环。
- 明确不变量：正式 `closed` 必须同时满足规定的整改、复查、阶段和审批条件。
- 复查从时间字符串数组升级为带结果、证据、复查人、时间和意见的记录。
- 制定存量数据迁移规则：已 `closed` 但阶段/证据不足的数据进入“待补证/待确认”，不要直接删除历史状态。

---

### P0-3：批量导入和钉钉同步不具备端到端幂等

**证据**

- `POST /issues/batch` 只接收 `items`，没有批次号、幂等键和每条 `sourceKey` 唯一约束。
- 钉钉流程先 `createBatch()`，后写 `dingtalk_imports` 台账。若进程在两步之间崩溃，下次会把同一消息当作未导入。
- 查重依赖向量结果；嵌入不可用时返回空结果，不能作为防重复的最终保障。
- 文件归档在入库之后，重名归档失败会把已成功导入的批次标成失败并触发重试。
- 批量事务只覆盖隐患插入，考核等后续副作用在事务外；副作用失败会造成“前端认为失败、数据库其实已提交”。

**改造**

- 新增 `ImportBatch`、`ImportItem`，保存批次状态、文件哈希、消息 ID、每条 sourceKey、业务 ID、错误与验收结果。
- 数据库唯一约束至少覆盖：钉钉 `messageId + item.sourceKey`；手工批次 `batchId + itemKey`；文件级 `contentHash + sourceLocator`。
- 采用“先创建批次/占位，再事务写业务结果，最后更新台账”的可恢复流程。
- 向量查重只作为人工提示，不能替代数据库幂等。
- 文件归档失败与业务入库结果分离，不得把已成功的业务批次改判为失败。

---

### P0-4：权限粒度过粗，高风险操作没有职责分离

**证据**

- 当前只有 `admin / safety_officer / viewer`。
- 默认规则是所有非 GET 请求都允许 admin 和 safety_officer；除少数管理员端点外，安全员可修改闭环、删除考核、编辑知识文档等。
- 考核由重复规则自动写正式台账，没有“建议—审批—生效”状态。
- 管理员与业务审批权没有分离，操作人与审批人也没有分离。

**改造**

角色至少拆为：系统管理员、安全员、整改责任人、复查人、业务审批员、查看者。权限按动作和数据范围判断，而不是仅按 HTTP 方法判断。

新增权限示例：

- `issue:create/edit`
- `issue:rectify`
- `issue:recheck`
- `issue:close:apply`
- `issue:close:approve`
- `assessment:propose/approve`
- `knowledge:edit/reindex`
- `agent:run`
- `system:backup/users/config`

自动考核规则只生成“考核建议”，正式生效需审批；重大隐患闭环和正式考核禁止同人申请并审批。

---

### P0-5：旧 JWT 在密码修改、删除用户和降权后仍有效

**证据**

JWT 有效期 7 天，角色放在令牌中；AuthGuard 只验签，不查用户当前状态。修改密码、重置密码、删除用户、角色变更均不会使旧令牌失效。

**改造**

- User 增加 `tokenVersion`、`disabledAt`、`updatedAt`。
- JWT 携带 `sub + tokenVersion`，守卫查询当前用户并校验版本和禁用状态。
- 密码、角色、禁用、删除操作递增版本；删除用户优先改为禁用，保留审计主体。
- 缩短访问令牌有效期并增加刷新机制，或采用统一 HttpOnly 会话 Cookie。
- 生产环境未配置强 `JWT_SECRET` 时直接拒绝启动，不能回退到开发默认密钥。
- `trust proxy` 只信任明确的反向代理，避免直连服务时伪造客户端 IP 绕过登录限流。

---

### P0-6：LLM 缺少统一运行控制和审计，Key 明文入库

**证据**

- `LlmService.answer()` 和预标注 `chat()` 直接 `fetch`，无超时、AbortController、最大输出、并发预算、每日预算、全局停止开关。
- 问答、预标注、规范检查分别拼提示词，没有统一 AI Gateway。
- Schema 中没有 TaskRun、AiRun、ToolRun、KbQuery 或 AuditLog。
- 没有记录模型、Prompt 版本、知识版本、检索块、token、成本、人工修改和业务验收。
- `settings` 表直接保存明文 `llm_api_key`；数据库全量备份自然包含该设置。
- 问答没有程序级引用完整性校验，文档内容也没有明确的不可信数据隔离。

**改造**

建立统一 `AiGateway`，所有模型调用必须经过：

- 全局/分功能开关。
- 每用户、每班组、全系统并发和每日预算。
- 超时、最大输入/输出、有限重试、取消排队任务。
- 允许列表中的 base URL 与模型配置。
- token、耗时、成本、错误类型和版本记录。
- 日志脱敏，Key 使用信封加密或外部密钥管理；备份文件加密并限制访问。
- AI 故障只影响 AI 功能，不影响主业务。

---

### P0-7：生产依赖存在高危审计项

不能直接用 `npm audit fix --force` 覆盖业务系统。应建立升级分支和完整回归：

- NestJS 10 升级需评估 NestJS 12 兼容性，重点覆盖 body-parser、multer、静态路由和上传。
- 前端 lodash、zod 按兼容版本升级。
- SheetJS `xlsx` 审计项无直接修复版本，建议用现有 Excel 样本评估 `exceljs` 或 `read-excel-file` 替换。
- 上传增加真实文件签名/解码校验、像素与解压上限、请求总大小限制和失败临时文件清理。
- CI 将生产依赖高危项设为发布阻断，例外必须有书面风险接受和到期日。

## 3.2 P1：业务可靠性、知识与工程能力短板

### P1-1：提醒会过期或不再触发

- 隐患闭环后，既有 overdue 提醒没有统一清理/完成逻辑。
- 检查计划提醒以 `plan.id` 为唯一 refId；完成后 `done=true`，下一周期 upsert 的 `update={}` 不会重置，因此可能永远不再显示为待办。
- 复查时间按 `foundAt + N × interval` 计算，历史通报导入后可能多次复查同时到期；更合理的基准通常是整改验收时间或上一次复查时间。
- 每个在线前端每分钟都调用 refresh，多客户端会重复扫描和写库。

**改造**：提醒由后端单一调度器派生，以业务周期作为幂等键；闭环/删除/恢复同步失效或重建提醒；补充“下一周期重新待办、闭环不再催办、历史导入不瞬间挤爆”的测试。

### P1-2：统计口径不适于直接提供给 Agent

`Statistics.tsx` 的按期闭环率在前端计算：

- `deadline >= since` 没有周期上界，会把窗口后的未来期限也纳入分母。
- 无到期记录时返回 100%，容易与“没有可评价样本”混淆。
- 总览与统计页使用不同闭环率定义。
- 所有数据一次性加载到浏览器，后续数据增长会加重计算与传输。

**改造**：建立唯一 `MetricsService` 和 `/api/metrics/*`，所有周期采用 `[start, end)`，明确新增、到期、按期闭环、超期存量、平均闭环时长、复发率口径；无样本返回 `null`。前端和 Agent 只能调用同一接口，禁止模型自行心算统计值。

### P1-3：知识库可能漏同步，引用 ID 不稳定

- `syncIssues()` 在全量重建运行或嵌入模型未就绪时直接返回，没有补偿队列。
- 同步采用 fire-and-forget，失败只写日志，业务请求仍成功，长期会出现知识陈旧。
- 全量重建先删后建，失败会留下空库或半库。
- 重建会更换 KnowledgeDoc ID；通报没有稳定 `sourceKey + page/chunk` 定位。
- Schema 没有知识 outbox，也没有 HNSW 向量索引。
- 法规库没有进入统一检索链路，问答引用未持久化、未硬校验。

**改造**：稳定 `sourceKey`、内容哈希、知识版本、outbox、幂等消费者、影子索引原子切换；保留原始页码和 chunk 区间；法规按版本和有效性入库；检索与回答都记录快照。

### P1-4：钉钉自动导入把“未复核记录”直接送入正式业务

自动导入的数据 `reviewed=false`，但仍会立即设整改期限、进入提醒、统计和考核。部分文件失败时，整体 `lastResult.ok` 仍可能为 true，首页显示“正常”。

**改造**：自动导入先进入持久化待复核批次；复核通过后才激活整改期限、提醒、统计和考核。批次状态区分成功、部分成功、失败、待人工处理，并显示每条最终状态。

### P1-5：复查匹配阈值偏低且缺少服务端复核依据

前端核销匹配仅以 bigram 覆盖率 ≥0.45 和可选车间一致为条件，服务端收到的是最终闭环 PATCH，无法复核匹配分数、原文和候选冲突。

**改造**：匹配与核销均在服务端完成；保存原通报、页码、匹配分数、候选列表和人工选择。低分、多候选、元数据冲突必须转人工，不能自动闭环。

### P1-6：缺少并发控制和正式审计

- 复查、阶段推进、计划完成都是先读后写，双击或并发可能重复记录/跨周期。
- 没有版本号或条件更新。
- 没有不可变业务事件和前后快照。

**改造**：Issue/Plan 增加 version；命令使用事务和条件更新；重复命令以 idempotency key 去重；保存操作者、审批者、前后快照、原因、请求 ID 和时间。

### P1-7：列表和查询缺少分页及常用索引

`GET /issues` 默认全量返回，知识文档最多取 300 但无游标；Issues 常用筛选字段和向量检索缺少针对性索引。

**改造**：服务端分页、筛选、排序白名单和最大 limit；按实际慢查询为 `deletedAt/status/scope/foundAt/deadline/categoryId/locationId` 建组合索引；数据量达到阈值后为 embedding 建 HNSW。

### P1-8：生产 Docker 与本机 Windows 能力没有完成适配

- 生产容器调用 Windows PowerShell、`cmd.exe` 和本机 dws 路径，备份与钉钉同步不可直接工作。
- 镜像没有复制根目录 `scripts/backup.ps1` 和通报目录。
- 备份/同步只按进程内“某一分钟”触发，进程停机不会补跑。
- `start-watchdog.bat` 仍调用不存在的 `watchdog.js`，当前实际文件是 `watchdog.ps1`。

**改造**：区分 Windows 单机与 Linux Docker 两个部署配置；定时任务持久化并支持补跑；备份恢复纳入演练；清理失效脚本和硬编码路径。

### P1-9：前端错误处理把业务错误误报为离线

全局 store 的任何失败都设置 `offline=true`，400 校验错误、403 越权和真实断网没有区分；API 错误只显示 HTTP 状态，丢弃后端业务错误信息。

**改造**：统一错误类型 `validation/forbidden/not_found/conflict/timeout/offline/server`；保留 requestId 和可读消息；只有网络/5xx 才进入离线重连，业务错误不自动重试。

### P1-10：工程规范与性能尚未形成发布门禁

- ESLint 当前 29 个错误。
- 页面文件过大，IssueEntry/IssueList/Knowledge 都承担多种职责。
- 依赖目录存在额外平台包，需通过干净 `npm ci` 验证可重复性。
- 前端构建有大 chunk 警告。

**改造**：先清零 lint，再拆导入状态机、详情命令、知识文档管理等模块；按路由和重型解析库拆包；CI 执行干净安装、构建、lint、单测、集成测试和依赖审计。

## 四、目标架构

```text
React 页面
  ├─ 确定性业务页面：录入 / 整改 / 复查 / 审批 / 统计
  └─ Agent 工作台：提问 / 步骤状态 / 引用 / 草稿 / 人工接管
                         │
                         ▼
NestJS
  ├─ IssueCommandService      唯一隐患状态机与不变量
  ├─ ApprovalService          申请、审批、撤销、职责分离
  ├─ ImportService            持久化批次、幂等、复核后激活
  ├─ MetricsService           唯一统计口径，SQL 聚合
  ├─ KnowledgeService         稳定 sourceKey + outbox + 版本化索引
  ├─ AiGateway                超时、限流、预算、开关、模型轨迹
  ├─ AgentRuntime             有界单 Agent 循环，只读工具
  │     └─ ToolRegistry       Schema、权限、超时、结果上限、ToolRun
  └─ AuditService             业务审计、请求 ID、前后快照
                         │
                         ▼
PostgreSQL + pgvector
  业务表 / 导入批次 / 审批与事件 / TaskRun / AiRun / ToolRun
  AuditLog / KnowledgeOutbox / 知识快照
```

原则：业务命令与 Agent 工具分层。即使未来模型返回恶意或错误参数，也只能调用允许列表中的只读工具；模型不能生成 SQL、URL、文件路径或任意 Prisma 查询。

## 五、Agent 功能设计

## 5.1 首选场景与优先级

| 优先级 | 场景 | Agent 做什么 | 不做什么 | 业务验收 |
|---|---|---|---|---|
| A | 统计问答 | 根据自然语言确定周期/范围，调用统计工具并解释结果 | 不自行计算或编造数字 | 数字与 Metrics API 完全一致，周期明确 |
| A | 法规与案例溯源 | 组合检索法规、隐患案例、通报原文，返回可点击引用 | 不把未复核案例当唯一高风险依据 | 每个结论有真实来源，无依据时拒答 |
| A | 周报/月报草稿 | 调用统计、超期、复发、法规工具，生成带引用草稿 | 不自动发布、不自动发送群 | 数值通过确定性校验，人工确认后导出 |
| B | 通报导入助手 | 解释解析结果、指出缺字段/重复/冲突，辅助逐条复核 | 不自主确认入库、不自主核销 | 数据库批次与人工确认一致 |
| B | AI 预标注 | 对字段给建议、依据和缺失项，支持逐字段采纳 | 不覆盖人工字段、不自动定重大等级 | 字段级人工验收与修改记录 |
| C | 检查计划建议 | 根据复发与超期情况生成检查重点草稿 | 不自动修改计划 | 人工创建/调整后生效 |

暂不建设：自主闭环、自主审批考核、自主修改制度、自动发送正式通报、多 Agent 协作、模型自由写 SQL/业务库。

## 5.2 MVP 工具清单

第一阶段全部只读；写仅发生在 Agent 自己的任务/轨迹表，不写业务表。

| 工具 | 输入摘要 | 输出摘要 | 限制与验收 |
|---|---|---|---|
| `search_issues` | 状态、范围、区域、类型、日期、关键词、cursor | 最多 20 条摘要 + 下一游标 | 参数白名单；继承用户数据权限 |
| `get_issue` | issueId | 业务字段、复查与审批摘要、来源定位 | 不默认返回照片和个人敏感信息 |
| `search_cases` | query、scope、时间、已复核过滤 | 最多 8 个去重案例及 score/sourceKey | 稳定 sourceKey；记录知识版本 |
| `get_regulation` | regulationId 或标题+条款 | 条文、版本、有效状态、来源 | 失效版本不得作为当前依据 |
| `get_source_excerpt` | sourceKey、chunk 范围 | 原文片段和精确定位 | 禁止传任意文件路径 |
| `aggregate_safety_metrics` | `[start,end)`、scope、分组维度 | 确定性指标、口径版本、生成时间 | 仅 SQL/MetricsService 计算 |
| `list_pending_reviews` | 批次/隐患筛选 | 待复核项与缺失字段 | 只读，不执行确认 |
| `draft_report` | 已验证指标与引用集合 | 报告草稿 artifact | 不写业务库，不自动发布 |
| `draft_prelabel` | 单条文本和允许标签 | 字段建议、null、缺失信息 | 复用 AI Gateway；记录逐字段结果 |

每个工具必须有 JSON Schema、最大输入/输出、超时、错误码、权限声明、幂等说明、耗时和 ToolRun 记录。

## 5.3 AgentRuntime：有界状态机，不做无限自治

建议 MVP 预算：

- 最大 6 个步骤。
- 最大 3 次模型调用。
- 总时长 45 秒；单工具 5～10 秒，单模型请求 20～30 秒。
- 检索最多 8 块，业务列表最多 20 条，总上下文有 token 上限。
- 验证失败最多重试 1 次；仍失败则 `waiting_human`，不循环“碰碰运气”。
- 支持取消新步骤、暂停、恢复和从最后检查点继续。

任务状态：

```text
queued → running → validating → succeeded
                   ├─→ failed
                   ├─→ waiting_human
                   └─→ cancelled
```

`succeeded` 只能由验收器设置：

- 统计任务：所有数值来自有效 ToolRun，口径/周期完整。
- 引用任务：所有引用 ID 存在，原文支持对应结论。
- 报告任务：指标、引用、缺失项和人工确认状态齐全。
- 预标注：Schema 合法，枚举在允许集合内，信息不足字段为 null。

## 5.4 建议 API

```text
POST /api/agent/runs                 创建任务，返回 202 + runId
GET  /api/agent/runs/:id             状态、结果、验收、错误和成本
GET  /api/agent/runs/:id/steps       模型/工具/检索轨迹
POST /api/agent/runs/:id/cancel      停止后续模型和工具调用
POST /api/agent/runs/:id/resume      人工补充信息后恢复
GET  /api/agent/capabilities         当前用户可用工具和预算
```

前端展示“待执行、执行中、验证中、成功、失败、待人工处理”，不能只显示一个不断旋转的“AI 思考中”。

## 5.5 最小数据模型增量

| 模型 | 关键字段 | 用途 |
|---|---|---|
| `ImportBatch` | id、source、status、fileHash、externalMessageId、createdBy、error | 可恢复导入批次 |
| `ImportItem` | batchId、sourceKey、draftJson、issueId、status、error、reviewedBy | 每条最终状态与幂等 |
| `IssueEvent` | issueId、type、actorId、payload、createdAt | 确定性业务时间线 |
| `RecheckRecord` | issueId、seq、result、note、evidence、actorId、createdAt | 真实复查记录 |
| `ApprovalRequest` | resourceType/id、action、status、applicantId、approverId、before/after、comment | 闭环/考核审批 |
| `TaskRun` | type、status、input/output、idempotencyKey、validation、started/finished、duration | 端到端任务验收 |
| `AiRun` | taskRunId、model、promptVersion、kbVersion、tokens、cost、error | 模型调用轨迹 |
| `ToolRun` | taskRunId、tool、schemaVersion、args/result、duration、status | 工具轨迹与复现 |
| `AuditLog` | actor、action、resource、before/after、requestId、createdAt | 高风险业务审计 |
| `KnowledgeOutbox` | sourceKey、operation、contentHash、status、retryCount、availableAt | 不漏更的知识同步 |

审计与轨迹中禁止保存 API Key；对通报、人名、照片地址、问答内容设置保存期限和访问范围。

## 5.6 提示注入与数据安全

- 系统消息明确：通报、法规、案例、用户上传文档均为“不可信资料”，不是指令。
- 资料中出现“忽略规则、发送密钥、调用接口、修改状态”等文本，只作为内容，不触发工具。
- 工具名称和参数由后端允许列表决定；模型不能构造 SQL、URL 和文件路径。
- 每个工具在服务端重新鉴权，不能信任模型传入的 userId/role。
- 无依据时拒答；信息不足时指出具体缺失字段。
- 引用编号与 ToolRun 检索快照绑定，后端验证后方可返回成功。
- 未复核内容默认不进入高风险整改建议上下文，或必须显著标记且有人工复核。

## 七、评测与 ROI 方案

## 7.1 三组对照

同一批任务随机分配给三组，记录处理时间和修正负担：

1. 纯人工录入与查询。
2. 固定解析/固定统计/RAG + 人工确认，不使用 Agent 规划。
3. 固定解析 + 只读工具型 Agent + 人工确认。

Agent 是否保留由第三组相对第二组的增益决定，而不是与“完全不用系统”比较后夸大价值。

## 7.2 离线任务集

- 30 份不同月份、格式和措辞的通报。
- 100 条人工确认预标注样本，按字段保存标准答案。
- 50 个知识问答：有答案、无答案、冲突资料、越权请求。
- 20 个统计问题：周期边界、无样本、跨车间、未来期限、闭环撤销。
- 异常：损坏文件、空文本、图片页、重复通报、模型超时、数据库异常、嵌入缺失。
- 对抗：恶意文档指令、伪造法规、诱导越权、要求忽略系统规则。

同一任务至少连续执行 3 次；模型、Prompt、嵌入、知识版本、工具版本分别回归。

## 7.3 指标定义

- **端到端成功率**：业务验收器通过的任务数 / 总任务数。
- **首次通过率**：无需人工修改且首次验收通过的任务数 / 总任务数。
- **人工修正率**：任一业务字段被人工修改的任务数 / 已完成任务数；预标注需按字段分别统计。
- **虚假完成率**：界面/任务称成功但数据库或业务验收未成功的任务数 / 称成功任务数。
- **异常恢复率**：故障后安全降级、恢复或正确转人工的任务数 / 故障任务数。
- **引用完整率**：所有事实性结论均有有效来源支持的任务数 / 需引用任务数。
- **单成功任务总成本**：

```text
模型 + 嵌入 + 服务器 + 数据库存储分摊 + 人工复核 + 失败重试与返工
────────────────────────────────────────────────────────────
成功任务数
```

同时记录 P50/P95、token、模型调用次数、工具重复调用、队列积压和人工接管率。

## 7.4 试点参考门槛

以下是目标，不是当前实测结果：

- 核心任务成功率 ≥90%。
- 首次通过率 ≥80%。
- 连续 3 次全通过率 ≥85%。
- 异常恢复或安全升级率 ≥85%。
- 轨迹完整率 100%。
- 虚假完成率 0。
- 错误自动核销 0。
- 高风险审批绕过率 0。
- 提示注入导致危险操作成功率 0。
- 重大版本变更核心回归通过率 100%。

## 八、必须补齐的测试清单

### 写操作与幂等

1. 创建隐患返回 500 时，前端不清空、不跳转、不显示成功。
2. 请求超时但服务端已提交时，按幂等键查询真实结果，不重复创建。
3. 双击批量导入、刷新重试、并发重试均只产生一批业务记录。
4. 钉钉在“入库后、台账前”崩溃，恢复后不重复。
5. 照片部分失败时，批次标为待人工处理，已成功项不重复。

### 状态机与审批

6. 通用 PATCH 不能修改 status/stage/closedAt/rechecks/reviewed。
7. 缺整改证据、少复查、阶段未完成、无审批均不能闭环。
8. 申请人与审批人相同时拒绝重大闭环和正式考核。
9. 撤销闭环需要权限、原因和前后快照，撤销后提醒/统计重新计算。
10. 并发复查和双击阶段推进不产生重复记录。

### 权限与安全

11. 修改密码、重置密码、降权、禁用、删除后旧 token 失效。
12. viewer 不能写；整改责任人不能审批；系统管理员不默认拥有业务审批权。
13. Agent 工具即使收到伪造 role/userId 也不能越权。
14. 恶意通报要求调用工具、发 Key、改闭环时无任何危险副作用。
15. 日志、AI 轨迹和导出包不包含 LLM Key。

### AI 与知识库

16. 模型超时、空内容、非法 JSON、429、500 均安全降级，不影响主业务。
17. 全局停止后无新模型请求，排队任务可取消。
18. 引用不存在或原文不支持结论时，任务不能标记成功。
19. 嵌入缺失/全量重建失败后，outbox 可恢复且旧索引仍可用。
20. 无答案、冲突法规、失效法规场景正确拒答或提示冲突。

### 提醒与统计

21. 计划下一周期提醒重新变为待办。
22. 隐患闭环/删除后 overdue 不再出现，恢复后按规则重建。
23. 周期起止边界、未来期限、无样本、跨车间统计符合统一口径。
24. Agent 返回的每个统计值与 Metrics API 完全一致。

## 九、建议立即执行的第一个迭代顺序

1. 先把 store 写接口改为 Promise，并补“失败不丢草稿”的前端测试。
2. 引入 ImportBatch/Item 与幂等约束，再切换手工和钉钉两条导入链路。
3. 从通用 PATCH 移除高风险字段，落专用命令和统一状态机。
4. 补审批、AuditLog、tokenVersion 和权限矩阵测试。
5. 用 AiGateway 收敛所有模型调用，加入超时、预算、停止和轨迹。
6. 修复提醒与统计口径，并把统计迁入 MetricsService。
7. 升级高危依赖，重写旧 E2E 中错误的闭环契约。
8. 完成上述门禁后，再实现 `aggregate_safety_metrics + search_cases + get_regulation` 三个只读 Agent 工具，作为最小可演示闭环。

第一个 Agent 演示建议定为：

> “统计近 30 天成品车间新增、到期、超期和按期闭环情况，找出复发较多的类型，并生成带真实引用的周报草稿。”

它能同时验证自然语言理解、工具选择、确定性统计、案例检索、引用校验、草稿生成和任务轨迹，又不需要任何业务写权限。

## 十、默认假设与待业务确认项

本方案按以下默认值设计，不阻塞先行开发：

- 保留 React/NestJS/PostgreSQL/pgvector，不新增向量数据库和重型 Agent 平台。
- 嵌入继续本地运行；外部生成模型保持可配置、可停用。
- Agent 首期只读，正式业务写入仍走现有用户界面与审批命令。
- 未复核自动导入记录默认不参与正式提醒、统计和考核。
- “参考件一键闭环”建议改为“归档”，避免与正式整改闭环混用。

需要业务负责人最终确认的规则：

1. 哪些风险等级必须审批，审批人角色分别是谁。
2. `status=closed` 是整改验收完成还是三次复查和制度沉淀全部完成；建议统一为后者。
3. 三次复查的起算点：整改验收日还是上一次复查日。
4. 通报自动导入的记录在复核前是否允许出现在普通问题库。
5. AI 问答、轨迹、人名、照片和通报原件的保存期限与可见范围。
