车间安全管理系统优化建议
——基于《Agent 业务项目评价指标体系》
一、总体优化方向
结合评价体系和项目现状，建议将项目定位调整为：
以确定性安全业务闭环为主体，以 AI 辅助录入、检索和草稿生成为增量，以人工复核和审批控制高风险操作。
现阶段不建议优先建设自主规划、多 Agent 协作或自动写业务库能力。项目当前的主要短板不是模型不够强，而是：
任务是否真正完成，缺少统一的业务验收标准。
AI 与业务操作的轨迹不完整。
状态、权限、审批和回滚约束不够严格。
缺少成功率、首次通过率、异常恢复率和单任务成本数据。
尚未用对照实验说明 Agent 相比固定工作流究竟增益多少。
按照附件要求，“Agent 声称完成”不能算任务成功，必须以业务规则、数据库状态或人工验收为准。
Agent 业务项目评价指标体系
因此，优化顺序应是：
先消除安全否决风险 → 再提高任务成功率 → 再建设 Harness → 最后验证 ROI 和推广价值。
目前不宜直接给出严谨的百分制总分，因为业务效果、任务成功率、P95 和成本等数据尚未实测，不能用主观评分替代。
二、优先解除安全与质量否决风险
这是扩大使用范围前的必要条件，不能用业务收益抵消。
1. 消除“虚假完成”
当前风险
前端没有等待创建隐患请求完成，就可能清空暂存并跳转。
通报核销可以直接把隐患改为已闭环，但没有完整复查和阶段记录。
AI 接口失败后，部分流程主要依赖统一离线提示，用户难以确认哪些数据真正写入。
优化动作
所有写接口返回可等待的 Promise，服务端确认后才更新页面。
导入增加批次号和幂等键，重复点击、超时重试不得重复入库。
页面展示每条任务的最终状态：待执行、执行中、成功、失败、待人工处理。
闭环成功必须由后端重新查询状态后确认，不能仅依据按钮操作。
建立 TaskRun，记录任务输入、执行状态、业务结果、错误和验收结果。
验收标准
虚假完成率为 0。
接口失败时草稿和照片不丢失。
同一批次重复提交不会产生重复隐患。
未满足复查、复核和审批条件的隐患无法进入闭环。
2. 统一高风险业务状态机与审批
优化动作
将隐患生命周期收敛为后端唯一状态机，禁止通过通用编辑接口直接修改：
status
stage
closedAt
rechecks

Text

复制
提交整改
验收整改
登记复查
申请闭环
审批闭环
撤销闭环
提出考核建议
审批考核
重大隐患闭环、正式考核、制度变更等操作，应具备：
参数校验。
操作人与审批人分离。
前后状态快照。
审批意见。
撤销和恢复机制。
完整审计记录。
验收标准
高风险操作审批覆盖率 100%。
审批绕过成功率为 0。
审计记录完整率 100%。
所有闭环都能追溯到整改证据、复查记录和审批人。
3. 增加停止、限流、回滚和人工接管
优化动作
为所有 LLM 请求设置超时、最大输出、并发数和每日预算。
对登录、上传、预标注、问答、重建索引分别限流。
批量预标注改为有界队列，避免 50 条串行请求长期占用连接。
增加全局 AI 开关，能够立即停止新 AI 请求并取消排队任务。
AI 故障不得影响隐患录入、整改和查询等主业务。
写操作使用数据库事务和幂等约束，不允许模型无限重试。
明确“系统异常时联系谁、由谁接管、如何恢复”。
验收标准
故障注入后不存在无限调用、持续扣费或重复写操作。
LLM 超时、限流、返回空内容、非法 JSON 时均能安全降级。
紧急停止和恢复演练通过率 100%。
三、按七类指标制定优化措施
1. 业务价值：20 分
当前差距
系统功能较多，但尚未量化：
每份通报人工录入需要多久。
AI 辅助后减少了多少时间。
人工复核成本是否抵消了模型收益。
错录、漏录和重复入库是否真正下降。
哪些功能值得复制到其他车间。
优化建议
先进行 2～4 周基线测量，至少比较三组：


方案	对比目的
纯人工录入与查询	建立业务基线
固定解析规则＋人工确认，不使用 LLM	判断固定工作流已经能解决多少问题
固定解析＋AI 预标注／RAG＋人工确认	测量 Agent 的真实增量价值
核心指标：
单份通报处理时长。
单条隐患录入成本。
首次录入准确率。
平均人工修正时间。
每百条漏录、错录和重复记录数。
闭环周期和超期存量。
单个成功任务总成本。
Agent 必要性结论应通过对照实验得出，而不是因为使用了大模型就默认成立。
2. 端到端任务效果：20 分
建议先把项目拆成四类可独立验收的任务，避免用“系统整体挺好用”代替任务评价。


核心任务	业务成功标准
通报导入	数据库记录与标准答案一致；字段完整；无错误核销；失败不丢草稿
AI 预标注	类型、等级、根因和建议达到人工验收标准；信息不足时返回空值
知识库问答	结论有真实引用支持；无依据时拒答；来源能定位原记录
统计与周报草稿	数值来自确定性统计接口；引用可核查；人工确认后才能发布
每类任务分别统计：
端到端任务成功率。
首次通过率。
人工修正率和修正时间。
返工次数。
错误漏检率。
虚假完成率。
整改闭环本身仍由确定性业务系统负责，不建议将“自主决定闭环”设为 Agent 任务。
3. 稳定性与环境适应性：15 分
优化动作
建立可重复运行的离线评测集：
30 份不同月份、格式和措辞的通报。
100 条人工确认的预标注样本。
50 个知识问答，包含有答案、无答案和冲突资料。
异常案例：损坏文件、空文本、图片页、重复通报、模型超时、数据库异常、嵌入模型缺失。
对抗案例：恶意文档指令、伪造法规、诱导越权、要求忽略系统规则。
执行三类测试：
重复测试：同一任务至少连续执行 3 次。
故障注入：验证超时、限流、工具报错后的恢复和转人工。
版本回归：分别更换模型、Prompt、嵌入模型、知识库和工具，观察哪一层造成退化。
试点参考目标
核心任务成功率 ≥90%。
首次通过率 ≥80%。
连续 3 次全通过率 ≥85%。
异常恢复或安全升级率 ≥85%。
重大版本变更后核心用例回归通过率 100%。
错误自动核销目标为 0，重大隐患场景应设置更严格门槛。
这些数值与附件的试点参考线一致，但不应直接套用到高风险自动决策场景。

工具层

每个工具需要：

幂等性说明。

第一阶段全部只读；写入类工具暂不开放给 Agent。
上下文层
使用稳定文档 ID 和业务 sourceKey，避免重建索引后引用失效。

信息不足时减少上下文并明确追问，而不是继续扩大检索量。
控制与验证层
即使暂不建设复杂 Agent，也应具备：
最大步数、时间和成本预算。
任务暂停、恢复和检查点。
防止重复执行的幂等控制。
引用、数值和业务状态的自动验证。
验证失败后的有限重试与安全转人工。
可观测层
每次执行记录：
Text

复制

知识库版本、检索块及分数、工具参数、工具结果、
最终输出、业务验收结果、人工修改、耗时、Token、成本
目标是全链路轨迹完整率 100%，并能够复现“为什么得到这个结果”。
5. 安全、权限与合规：15 分
权限与数据安全
将管理员、业务审批员、安全员、整改责任人和查看者分离。
管理员不默认拥有业务审批权。
修改密码、删除用户或降权后，旧令牌应失效。
LLM Key 加密保存，禁止进入日志、AI 轨迹和普通备份下载包。
明确通报、人名、照片和 AI 问答记录的保存期限与访问范围。
注入与恶意文档防护
将检索资料视为不可信数据，而不是系统指令。
对通报中的“忽略之前规则”“发送密钥”“调用接口”等文本进行隔离。
工具采用允许列表，模型不能动态构造 URL、SQL 或文件路径。
法规结论必须关联真实法规条目和版本。
未复核内容不得作为高风险整改建议的唯一依据。
上线门槛
严重越权和重大敏感数据泄露为 0。
高风险审批绕过率为 0。
提示注入导致的危险操作成功率为 0。
所有高风险操作均可审计、停止和恢复。

成功任务数
建议增加：
按任务统计 P50、P95 完成时间。

每次问答的检索、生成和人工复核耗时。

优化重点应放在“提高首次通过率”，因为低模型价格但高返工率，实际成本可能更高。
7. 人机协作与组织保障：5 分
交互优化
信息不足时，AI 应指出缺少哪个字段，而不是直接给建议。
预标注支持逐字段采纳、拒绝和修改。
每条建议显示依据案例或原文片段。
人工复核记录复核人、时间、意见和修改差异。
转人工时携带当前草稿、检索资料和失败原因，避免用户重新开始。
记录采纳率、持续使用率、接管率和用户满意度。
同时监控两类问题：
应该转人工却没有转，形成业务风险。
不应转人工却频繁转，抵消自动化价值。
责任机制
建议明确三类负责人：
业务负责人：安全员或车间主任，负责业务规则和验收。
技术负责人：负责模型、接口、数据、发布和故障恢复。
风险负责人：负责权限、合规、高风险审批和事故处置。
四、推荐实施路线
第一阶段：安全与正确性加固，1～2 周
优先完成：
修复异步入库和虚假完成。
统一隐患状态机及闭环条件。
修复周期提醒和统计口径。
增加幂等、事务、DTO 和并发控制。
增加 AI 超时、限流、预算和紧急停止。
建立高风险操作审计和审批。
处理高危生产依赖。
阶段出口：不存在安全否决项，核心写操作可追溯、可恢复。
第二阶段：评测与 Harness 建设，2～6 周
建立标准任务集和人工基线。
建设 TaskRun、AiRun、AuditLog。
建立自动验收、重复测试、故障注入和版本回归。
修复知识库稳定 ID、同步 outbox 和引用定位。
建立任务成功率、首次通过率、人工修正率和成本看板。
将核心回归纳入 CI。
阶段出口：核心指标达到双方约定的试点门槛，轨迹完整率达到 100%。
第三阶段：验证 Agent 增量价值，6～12 周
先上线只读工具型 Agent。
对比固定工作流与 Agent 的质量、时间和总成本。
仅在确有增益的场景保留 Agent。
优先扩展统计问答、法规溯源和周报草稿。
评估向其他车间复制时，分类、法规、流程和权限能否配置化。
自动写业务库能力另行立项评审，不作为本阶段默认目标。
阶段出口：Agent 相比固定工作流具有明确质量或成本收益，才扩大应用范围。
五、最终验收建议
每次试点或上线评审，都应分别输出：
业务分：效率、质量、ROI、复用价值。
Agent 任务分：成功率、首次通过率、修正负担、稳定性。
Harness 分：工具、上下文、控制、验证、轨迹和可维护性。
安全结论：是否存在否决项。
成本与性能：单成功任务成本、P95、资源和容量。
典型失败案例：失败原因属于模型、任务设计、工具接口还是运行控制层。
发布结论：通过、限制范围试点、整改后复评或停止。
评测应坚持“任务集＋对照组＋模型与 Harness 分离＋离线与线上结合”的方法，避免把一次成功演示当成系统能力。
