# 车间知识库设计方案 · 详细版

> 目标：把系统里已有的隐患、整改、复查、参考标注、通报数据组织成"能问答"的私有知识库，用大模型做检索增强生成（RAG）。
> 原则：**只根据库里的内容回答、每条结论带来源、答不了就说没有**——安全生产场景，宁可拒答不可编造。
> 配套阅读：[设计文档.md](设计文档.md)、[开发日志.md](开发日志.md) 第十七阶段遗留计划

---

## 一、定位与边界

**是什么**：成品车间私有安全知识问答系统。安全员问"动火作业要注意什么""咱们车间什么问题容易复发"，系统从自己的历史数据里找答案，附出处。

**不是什么**：
- 不是通用 ChatGPT（不回答库外知识，不做闲聊）
- 不是自动决策系统（AI 只提供参考，整改决策永远在人）
- 不上传照片（只处理文本，照片走现有 uploads 体系，不进向量库）

**服务对象**：安全员（日常问答）、管理员（全部功能 + 知识库维护）。

---

## 二、知识资产盘点（现状即可入库，零手工录入）

| 资产 | 现状规模 | 知识库角色 |
|------|----------|-----------|
| 隐患 + 整改记录 + 复查结论 | 数十条（持续增长） | **案例块**——"什么问题/依据哪条/怎么改的/复发没有" |
| 参考标注（其他车间教训） | 47+ 条 | **教训块**——"别车间的教训 → 咱们要注意什么" |
| 厂督察通报 | 8 份（逐页） | **通报块**——原汁原味的检查记录 |
| 规程条文 | 散在隐患的"《××规定》"引用里 | **规程块**——问答时精确引用的法规定锚 |

**核心洞察**：每条已闭环隐患都是一份微型教案（问题 → 法规依据 → 整改做法 → 复查结果），这是花钱买不来的私有语料，也是与通用安全问答产品的根本差异。

## 三、总体架构

```
浏览器（知识库页/录入联动）
    │ POST /api/kb/ask {question}            ← RBAC 鉴权（viewer 也可问）
    ▼
后端 ai 模块（NestJS，新增）
    │ 1. 查询清洗（去空白、限长）
    │ 2. 嵌入 API：question → 向量（国内 API，服务端调用）
    │ 3. pgvector：余弦相似度 topK=10（现有 PostgreSQL，加扩展即可）
    │ 4. 重排（可选，二期）：取 top 5
    │ 5. 拼装提示词：检索块 + 编号 + 用户问题
    │ 6. 大模型 API：流式生成（服务端持有 Key，浏览器不接触）
    │ 7. 审计：问题/检索命中/答案 落库
    ▼
返回：答案（带引用编号）+ 来源卡片（可点跳转原始隐患/通报）
```

**关键决策**：
- **不引入新数据库**：PostgreSQL 加 `pgvector` 扩展，备份/权限/事务全沿用现有体系
- **Key 只在服务端 `.env`**：前端永远拿不到大模型 Key
- **LLM 故障降级**：接口超时/报错时返回明确提示"知识库暂时不可用"，主业务流程零影响

## 四、知识建模与分块策略

不同内容用不同切法，元数据尽量丰富（后面过滤、引用、跳转都靠它）：

### 4.1 案例块（隐患闭环时自动生成，增量入库）

```
标题：{类型} · {区域} · {问题摘要（≤30字）}
正文：
【问题】{description}
【依据】{不符合《××规定》（如有）}
【风险等级】{riskLevel}　【整改期限】{deadline 及是否超期}
【整改情况】{fixNote / status 流转时间线}
【复查结论】{rechecks 次数/结果，复发情况}
元数据：sourceType=issue, sourceId, scope(成品/参考), category, location,
        closedAt, overdue(bool), recheckCount
```
- 入库时机：隐患状态变 `closed` 时自动生成摘要块；编辑后 upsert
- 这是知识库的主体，未来 80% 的问答命中它

### 4.2 教训块（参考标注）

```
标题：其他车间 · {车间} · {问题摘要}
正文：{原始描述}【对成品车间的参考】相似点：{similarity}；注意事项：{caution}（重要性：{relevance}）
元数据：sourceType=annotation, sourceId, relevance(high/medium/low), workshop
```
- 全量存量入库一次；标注更新时 upsert
- `relevance=high` 的块在检索排序里加权（重要性高两倍权重）

### 4.3 通报块（导入通报时逐页入库）

```
标题：厂督察通报 {期号} · 第 N 页 · {车间}
正文：该页完整文字（已按现有解析器提取）
元数据：sourceType=report, sourceFile, pageNo, workshop, 是否被标为参考
```
- 导入确认生效时逐页入库；原始页文字本身就是最小切分（不再二次切块）

### 4.4 规程块（先抽目录后维护）

- **一期**：从全库隐患提取"不符合《…》"引用 → 去重 → 生成**规程目录块**（规程名 + 被引次数 + 关联隐患列表）。文本不全也能问答"哪条规定被违反最多"
- **二期**：管理员手工补录重点规程条文（知识库页加"规程维护"小入口），补一条问答质量升一截

### 分块通用规则

- 单块 ≤ 500 字（超过的案例按"问题/整改"拆两块）
- 每块必须有 `sourceType + sourceId` ——答案引用要能跳回原始记录，这是防幻觉的物证
- 删除隐患/标注时级联删块（外键或触发逻辑），保证库与业务数据一致

## 五、存储设计（Prisma schema 草案）

```prisma
model KbChunk {
  id         String   @id @default(cuid())
  type       String   // case | lesson | report | regulation
  sourceType String   // issue | annotation | report | regulation
  sourceId   String   // 原始记录 id（或 report 的 file+page）
  title      String
  content    String
  metadata   Json     // scope/category/relevance/overdue/recheckCount...
  vector     Unsupported("vector(1024)")?
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
  @@index([type, sourceType])
}
```

- 迁移：`CREATE EXTENSION IF NOT EXISTS vector;` + HNSW 索引（`vector_cosine_ops`）
- 存量脚本：一次性把现有 issue/annotation/report 全量切块入库（半天工作量，纯脚本）
- 另建 `KbQuery` 审计表：`question / chunksUsed(json) / answer / durationMs / createdBy`，用于评估与回溯

## 六、模型选型与成本（务实估算）

| 用途 | 推荐 | 理由 |
|------|------|------|
| 嵌入 | 通义 text-embedding-v3/v4 或 BGE-M3（SiliconFlow 等聚合平台） | 中文效果扎实、按 token 计价极便宜 |
| 生成 | DeepSeek-V3 / 通义千问 / Kimi 任一 | 中文长文好、价格低、国内合规 |
| 重排（二期） | bge-reranker-base | top10→top5 提精度 |

**成本估算**（几十条隐患 + 8 份通报，块数约 200~400）：
- 存量嵌入一次：≈ 几十万 token 的零头，**不足 1 元**
- 日常使用：每问一次 ≈ 1.5K token（检索块）+ 生成 ≈ 1K token，按 DeepSeek 现价 **每次不到 1 分钱**；每天问 50 次，月成本 **< 10 元**
- 结论：不需要本地部署，API 是最优解（本机也跑不动本地大模型）

**数据出域**：通报属厂内资料——选国内 API 已满足大部分要求；更进一步可在入库前把具体人名做脱敏占位（"张三"→"当事人"），问答时再还原。

## 七、RAG 查询链路（一期细节）

1. **接收问题**：限 500 字；viewer 角色也可提问（只读不违背 RBAC）
2. **嵌入**：调用嵌入 API 得向量（带 3 秒超时）
3. **检索**：`ORDER BY vector <=> $1 LIMIT 10`，过滤条件：scope/时间范围（问题里出现"最近"时加 90 天过滤）
4. **拼装上下文**（编号即引用锚点）：

```
[1] 案例｜动火作业 · 顶吹炉车间 · 电焊未佩戴防护面罩
【问题】…【依据】不符合《安全操作规程》…【整改】…【复查】…
[2] 教训｜其他车间 · 电解三车间 · 吊装吊臂下站人 …
[3] 通报｜厂督察通报第 538 期 · 第 4 页 · …
```

5. **系统提示词**（全文，这是质量的核心）：

```
你是成品车间的安全知识助手。你的唯一信息来源是下面编号的资料块。
规则：
1. 只根据资料块回答。资料里没有的，明确说"知识库里没有找到相关记录"，绝不编造。
2. 每个结论后面用 [编号] 标注来源；可以引用多个块。
3. 引用块之间的矛盾要指出来，不要和稀泥。
4. 回答用车间里的大白话，先给结论，再说依据。200 字以内，能短则短。
5. 涉及具体整改决策，结尾加一句"最终怎么定，请和安全员/主任确认"。
```

6. **生成**：temperature=0（确定性优先），max_tokens≈600，超时 30 秒
7. **返回答案 + 来源卡片**（标题/类型/摘要，点击跳 `/issues?id=xxx` 或通报详情）
8. **落审计**：问题、命中块、答案、耗时入库

## 八、前端形态

**知识库页（/kb）**：
- 问答主界面：提问框 + 回答气泡 + 来源卡片列表
- 历史：本次会话问答记录（localStorage 即可，不落库）
- 反馈：每条回答"有用 / 没用"按钮（点"没用"记录到审计表，供改进）
- 管理入口（仅 admin）：规程条文补录、入库状态一览（各类型块数、最近入库时间）

**录入联动（二期，价值最高）**：
- 手动录入填标题/描述时，防抖 1.5 秒自动检索相似案例，浮层提示"库里有 N 条类似问题，当时是这么改的"——**新人站在老师傅肩膀上**

---

## 九、质量保障与运营

1. **评估集**：上线前手工攒 20 条标准问题（"动火注意什么""咱们复发率最高的问题""去年超期最多的是哪类"…），每次改动提示词/换模型后跑一遍，对比答案质量——没有评估集的 RAG 等于裸奔
2. **拒答率监控**：审计表统计"未找到相关记录"占比，>30% 说明知识覆盖不够，补规程块
3. **引用完整性**：生成后程序校验答案里的每个 [编号] 都真实存在于本次检索块，不存在则丢弃重生成一次（硬防幻觉）
4. **新鲜度**：闭环即入库，知识库永远与业务数据同步；审计表每周看一眼

## 十、分阶段路线图

| 阶段 | 内容 | 工作量 | 产出 |
|------|------|--------|------|
| **P0 地基** | pgvector 扩展 + KbChunk 表 + 存量入库脚本（案例/教训/通报三类块） | 半天 | 向量库就绪，有数据 |
| **P1 问答** | /api/kb/ask + 系统提示词 + /kb 问答页 + 来源跳转 | 1~2 天 | 能在系统里提问 |
| **P2 联动** | 录入页相似案例浮层 + 评估集 + 拒答率监控 | 1 天 | 录入提效，质量可控 |
| **P3 深化** | 规程条文维护入口 + 周报生成引用知识库 + 重排 | 2~3 天 | 问答质量上一个台阶 |

每阶段独立可上线、可回滚（ai 模块整体一个开关），不影响现有 47 项回归覆盖的主流程。

## 十一、风险与对策

| 风险 | 对策 |
|------|------|
| 大模型编造 | 引用编号硬校验 + temperature=0 + 拒答模板 + 只喂检索块不喂模型自由知识 |
| 答案看着对其实错 | 来源卡片强制可见；涉及决策必带"请与负责人确认"结尾 |
| API 挂了/欠费 | 降级提示"知识库暂不可用"；主流程零依赖 |
| 数据出域顾虑 | 国内 API + 可选人名脱敏；Key 服务端保管；审计留痕 |
| 知识覆盖不足导致常拒答 | 拒答率监控 + 规程块补录 + 通报持续入库 |
| 成本失控 | 每问限长、限频（每用户每分钟 10 次）；审计表盯用量 |

---

## 十二、与主系统的关系

- ai 模块独立于现有 7 个业务模块，只读业务数据、只在 KbChunk 上写
- 不改动现有表结构（只加新表），现有 47 项回归全部不受影响
- 权限沿用 RBAC：提问全员可用，维护仅 admin
